# PRD · 大富翁 Monopoly Web · v1.0

> **给 Agent 的解析说明**：本文档中 `REQ-*`（需求）、`AC-*`（验收标准）、`M-*`（指标）、`NFR-*`（非功能）、`R-*`（风险）、`OQ-*`（开放问题）是规范性条目，编号稳定、可被引用；其余章节为背景与论证，不构成约束。所有"现状"数值均可在附录 A 的命令下复现，复现口径写在表格的"口径"列。判断"是否达成"只依据第 5 章的指标表与 §4.8 的完成定义（DoD）。

v1.0 相对 v0.1 的实质性结论变化（供快速 diff）：

1. **"回合上限只是兜底"这一判断被数据否定**：40 局中 35 局靠上限判胜（87.5%），仅 5 局靠破产结束。
2. **"存档成本低"不成立**：RNG 状态、牌堆顺序、牌堆游标均在引擎状态对象之外，`JSON.stringify(state)` 无法续玩。
3. **优先级调整**：拍卖（RICE 90）先于交易（RICE 48）落地；交易仍需实现，但不再是第一顺位。
4. **新增一项规则保真缺口**：破产清算时房屋价值被直接清零，未按官方折算给债权人。

## 1. 一句话概要

一个零依赖、可离线、规则可复现的浏览器大富翁：v1.0 已交付标准 40 格规则与可复现对局，但 87.5% 的对局靠回合上限截断判胜，说明玩法尚未自然收束；本期（v1.x）只做两件事——**让对局自然收敛**（拍卖 + 交易 + 规则修补）与**让对局可存续**（快照重构 + 存档），并把这些能力全部纳入可测的验收口径。

## 2. 地基 · 为什么做（WHY）

### 2.1 问题与背景

浏览器里能玩的大富翁分两类：一类"重"（依赖框架、打包器、`node_modules`，克隆后要 `npm install`），一类"浅"（规则被砍到只剩掷骰买地，缺拍卖、交易等核心机制，且不开源、不可离线）。本项目的缺口定义是：**一个轻、真、可改、可离线**的标准规则实现。

"真"的判据不是"复刻所有变体"，而是：把标准 40 格规则忠实落地，并把"有意简化 / 未实现"的差异**显式声明**；声明必须出现在用户能看到的地方（产品内 + README），而不只是开发文档里。

同时它是维护者的学习载体：实践"引擎与界面分离""纯逻辑可测""种子随机可复现"。

### 2.2 目标用户与 JTBD

| Persona | 描述 | JTBD | 证据状态 |
|---|---|---|---|
| A 休闲玩家 | 想立刻开一局，不装东西、可离线 | 我只有几分钟，想在浏览器里玩一局规则可信的大富翁，且不需要任何准备 | **假设**（无一手调研；验证方式见 OQ-06） |
| B 前端/开源学习者 | 想要零依赖、有测试、架构清晰的参考实现 | 我在学引擎设计 / AI 决策 / ES Modules 工程化，想要一份可读的参考代码 | **假设**（可由 issue 类型分布间接验证） |

### 2.3 目标与非目标

**目标（可判定）**

- G1：标准 40 格规则实现，且差异表（§6.2）中每一项都能在产品内被看到、被解释。
- G2：五项架构红线（§8.1）在任何一期交付后仍成立，且可被命令验证。
- G3：外部贡献可进入：CONTRIBUTING 存在、issue/PR 模板存在、单测门禁在 CI 上生效。

**非目标（明确不做）**

- 不做商业化（无内购、广告、账号体系）。
- 不追求覆盖所有官方变体 / 扩展包 / 主题皮肤。
- v1.x 不做移动端原生 App。
- 不替代官方商业产品；不使用官方商标素材（见 R-08）。

### 2.4 产品定位

> 面向"想玩一局可信大富翁"的人，以及"想读一份干净实现"的开发者，本项目是**唯一同时满足零依赖、可离线、规则可复现**的浏览器实现。

### 3.3 已知缺口（本期输入）

1. **玩法未自然收束**：B-07/B-08/B-09 构成同一事实的三个侧面——绝大多数对局靠 150 回合上限判净资产分胜负。v0.1 把它描述为"兜底"，与数据不符。
2. **拍卖缺失导致产权空转**：放弃购买即流拍，地块永久无人持有，降低破产概率。
3. **交易缺失导致玩家无法主动谈判**：这是官方规则中实现"资产再配置"的主要手段。
4. **存档不可续**：`state` 仅含棋盘与玩家数据；`rng`（游标）、`decks`（洗好的牌堆）、`deckIndex`、`maxTurns` 都在 `Game` 实例上，恢复后会重新洗牌、随机数重置，与"同种子必出同局"的承诺冲突。
5. **破产清算丢失房屋价值**：清算时 `houses` 直接置 0，房屋价值未按"半价卖回银行"折算给债权人。
6. **规则差异只在 README**：产品内无任何"这是简化实现"的提示，违反 §2.1 的"显式声明"承诺。

## 4. 定义 · 本期做什么（WHAT）

### 4.1 范围与优先级（RICE）

RICE = (Reach × Impact × Confidence) / Effort；Reach 用受影响玩家占比，Impact 用 0.25/0.5/1/2/3，Confidence 用 0-1，Effort 用人日当量。

| 编号 | 项 | Reach | Impact | Conf | Effort | RICE | 结论 |
|---|---|---|---|---|---|---|---|
| REQ-AUCT | 拍卖流程 | 100% | 2 | 0.9 | 2 | **90.0** | Must，第一顺位 |
| REQ-TRADE | 地产交易 | 100% | 3 | 0.8 | 5 | 48.0 | Must，第二顺位 |
| REQ-STORE | 存档 / 断点续玩（含快照重构） | 60% | 2 | 0.6 | 4 | 18.0 | Should |
| REQ-RULE | 规则保真修补（破产清算、文案、差异可见化） | 100% | 1 | 0.9 | 1 | 90.0 | Must（与拍卖并列，成本极低） |
| REQ-FX | 音效与动画强化 | 50% | 1 | 0.7 | 3 | 11.7 | Should |
| REQ-ONLINE | 联机对战 | 40% | 3 | 0.4 | 13 | 3.7 | Could，需 ADR-001 |

> 与 v0.1 的差异：拍卖的 RICE 高于交易（成本低、确定性强、直接消除"流拍即消失"的失真），因此先做拍卖；规则修补成本最低且直接影响核心承诺，与拍卖并行。交易仍为 Must，但排在拍卖之后。

### 4.2 REQ-AUCT · 拍卖

**规则细则（实现口径，需与 §6.2 差异表同步）**

- 触发：玩家放弃购买（`skipBuy`）后立即进入拍卖，不允许"流拍即消失"。
- 参拍资格：所有未破产玩家，包含当前回合玩家。
- 竞价形式：**轮次制顺序竞价**（简化：官方为公开竞价）。每轮每人一次机会，最小加价 10，可选 pass；连续一轮无人加价即由最高价者成交。
- 成交结算：扣款、转移产权、可立即建房（若满足均富与整组条件）。
- 无人出价：流拍，由银行持有（保持可再次被拍卖）。
- 破产处理：任一出价者现金不足而破产时，其出价作废，拍卖继续；破产玩家退出竞拍。
- 序列化：拍卖状态必须进入 `state`（`state.auction = { square, bids, high, turnOrder }`），保证快照可续。

**验收标准**

- AC-AUCT-01：放弃购买后 1 个引擎动作内进入 `phase = 'auction'`，且 `state.auction.square` 等于该地块索引。
- AC-AUCT-02：4 名玩家各 pass 一次后，拍卖以流拍结束，`state.owner[square]` 不存在，`state.auction` 清空。
- AC-AUCT-03：最高价成交后，买家现金减少额 = 成交价，产权转移，且该动作可被快照恢复（见 AC-STORE-03）。
- AC-AUCT-04：竞拍者现金不足且无法变卖时，出价被拒绝并记为 `invalid`，拍卖不中断。
- AC-AUCT-05：单测覆盖 ≥ 8 例（正常成交、流拍、破产退出、连续加价、最小加价校验、参拍资格、结算后建房资格、序列化往返）。
- AC-AUCT-06：40 局四人模拟中，`errors` 记录为 0，且 M-01 指标相较 B-07 基线有可测量的下降（见 §5.4 的实验设计）。

### 4.3 REQ-TRADE · 地产交易

**规则细则**

- 可交易资产：现金、地产（含已抵押地产）、出狱卡。
- 禁止：玩家之间直接买卖房屋（官方规则：房屋只能按半价卖回银行）；带房地产必须先卖空房屋才能交易。
- 参与方：仅未破产玩家；AI 与人可互相发起。
- AI 估价：`estimateValue(square, ownerId)` 纯函数，输入为状态与产权，输出为现金当量；报价与估价偏差必须 ≤ 15%（防止"随意报价"式实现）。
- 协商上限：单次交易提案最多 2 轮还价，超时/拒绝即终止，避免 UI 死循环。
- 状态：`state.trade = { from, to, offer, request, round }` 进入 state，可快照。

**验收标准**

- AC-TRADE-01：`decide(game)` 在存在可交易资产时能产出 `{ type: 'proposeTrade', ... }` 动作，且该函数无副作用（连续调用两次不改变状态）。
- AC-TRADE-02：`estimateValue` 对同一状态幂等，且对"对方色组完整性"敏感（构造两组对照状态，估价差 > 0）。
- AC-TRADE-03：交易成交后，双方现金与产权变更守恒（现金总量 + 产权数量不变），且带房地产无法被交易（返回明确错误码）。
- AC-TRADE-04：人类可发起 / 还价 / 接受 / 拒绝；拒绝后状态与交易前逐字段一致（含 `state.trade` 清空）。
- AC-TRADE-05：单测覆盖 ≥ 10 例（现金交易、地产+现金、抵押地产、出狱卡、带房拒绝、AI 估价偏差、还价轮次上限、拒绝回滚、破产方禁入、快照往返）。
- AC-TRADE-06：40 局四人模拟 `errors` 为 0；且 M-03（平均破产人数）相对基线 0.6 提升。

### 4.4 REQ-RULE · 规则保真修补

- AC-RULE-01：破产清算时，房屋按半价折算为现金加入债权人所得（或按官方流程先卖房再分配），单测覆盖"带 3 栋房破产"场景。
- AC-RULE-02：把"免费停车"文案从"休息一回合"改为"无效果（原版无奖金）"，避免被误读为停一轮。
- AC-RULE-03：规则差异表（§6.2）在 UI 中可访问（开局弹窗内一行"本实现与官方规则的差异"入口），点击后展示完整差异列表。
- AC-RULE-04：README 与 §6.2 的差异条目逐条一致（用脚本或人工清单核对，记入 PR checklist）。

### 4.5 REQ-STORE · 存档 / 断点续玩（含前置重构）

**前置需求（v0.1 低估的部分）**

- REQ-STORE-01：把 `rng` 游标、`decks`（洗好的牌堆）、`deckIndex`、`maxTurns` 纳入可序列化的 `state`（或提供 `toSnapshot()/fromSnapshot()` 显式包含它们）。**这是本项的主要成本，必须单列排期。**

**验收标准**

- AC-STORE-01：`snapshot = game.toSnapshot()`，`Game.fromSnapshot(snapshot)` 后，连续 200 次 `roll()` 的骰点序列与未中断对局**完全一致**。
- AC-STORE-02：恢复后的牌堆顺序与牌堆游标一致（连续抽 30 张牌，顺序与未中断对局一致）。
- AC-STORE-03：拍卖 / 交易进行中的快照恢复后，可继续完成该流程。
- AC-STORE-04：快照 JSON ≤ 200 KB（`log` 保留 200 条上限），损坏或版本不符时给出明确提示且不破坏既有存档。
- AC-STORE-05：localStorage 键带 schema 版本号；schema 升级不静默丢弃旧档。

### 4.6 REQ-FX · 音效与动画（Should）

- 目标：提升首局留存与手感，不改变规则。
- 约束：音效必须可关闭、默认静音；不引入外部资源依赖（可内联 base64 或程序化生成）；动画不得阻塞引擎动作。
- AC-FX-01：关闭音效后无任何音频请求；AC-FX-02：AI 对局加速（`speed=0`）时动画不成为瓶颈（单回合渲染 ≤ 16ms）。

### 4.7 REQ-ONLINE · 联机（Could，需 ADR-001）

- 决策点（OQ-01）：WebRTC P2P（手工交换 SDP，无需服务器但体验差）vs 最小信令服务器（体验好但引入部署依赖与"零依赖"红线例外）。
- 本阶段只要求：产出 ADR-001（选项、成本、红线突破评估、回滚方案），不要求实现。

### 4.8 完成定义（DoD）

任一 REQ 视为完成，必须同时满足：

1. 代码合入主分支，`node --test` 全绿且新增用例数达标；
2. `node scripts/simulate.mjs 40 4` 无 `errors`，且相关指标写入 §5 指标表并更新基线；
3. 对应 AC 逐条在 PR 描述里给出证据（命令 + 输出片段）；
4. 文档（README 的规则边界表 / §6.2 差异表）同步更新；
5. 架构红线（§8.1）未被破坏，若破坏则附 ADR。

## 5. 执行 · 怎么衡量（HOW & MEASURE）

### 5.1 指标结构

- **主指标（决定"这件事成没成"）**：自然结束率、撞上限判胜占比、平均破产人数。
- **护栏指标（决定"有没有搞坏"）**：单测通过、模拟 errors = 0、快照一致性、首屏与帧时间。
- **反向指标（防止用错误方式达标）**：单局回合数膨胀、人类玩家净资产被 AI 系统性压制、UI 交互步数膨胀。

### 5.2 指标表（基线 → 目标）

| 编号 | 指标 | 基线（实测） | 目标 | 口径 / 判定方式 |
|---|---|---|---|---|

### 5.3 质量门禁（必须守住）

- GATE-01：`node --test` 全绿，失败即阻断合并。
- GATE-02：`node scripts/simulate.mjs 40 4` 的 `errors` 为空；`未结束` 必须为 0（这一条由回合上限保证，**不能作为收敛性证据**）。
- GATE-03：新功能 PR 必须附带对应指标的前后对比。
- GATE-04：架构红线命令化校验（引擎无 DOM 引用、`src/engine` 不 import `src/ui`）。

### 5.4 实验设计（如何证明拍卖/交易真的有效）

因为拍卖与交易会同时改变对局形态，采用"单变量叠加"：

1. 基线：当前 `main`（已记录 B-04~B-10）。
2. 加拍卖（不合交易）→ 跑 200 局四人（同 200 个种子），记录 M-01/M-02/M-03/M-04。
3. 再加交易 → 同 200 个种子，记录同样指标。
4. 判定：M-01 至少下降一半、M-02 至少提升至 70%，否则先调 AI 策略而不是继续加功能。

> 200 局样本以降低方差；报告必须给出种子区间与命令，便于第三方复现。

### 5.5 遥测取舍（明确决定）

- v1.0 **不引入任何上报式遥测**（与零依赖、离线、无账号一致）。
- 允许：本地 `localStorage` 计数（完成局数、放弃局数、交易次数），仅用于开发者自查与本地展示，**不上报、可一键清除**。
- 因此 M-07/M-08 只采用 GitHub 公开数据；M-C1/M-C2 用本地计数在自测中采集。

## 8. 架构红线与例外流程

### 8.1 五项红线（任何 PR 破坏即拒绝）

1. 引擎零 DOM：`src/engine/*` 不引用 `document` / `window`。
2. AI 纯函数：`decide(game)` 与 `estimateValue(...)` 无副作用、可重复调用。
3. 数据 / 规则分离：加卡改 `cards.js`，加地改 `data.js`，不改 `game.js` 的分支结构。
4. 零运行时依赖 / 可离线：`package.json` 的 `dependencies` 必须为空；构建步骤必须为 0。
5. 可复现：同种子同动作序列必出同局，且该性质在存档恢复后仍成立（AC-STORE-01/02）。

### 8.2 例外流程

- 破坏任一红线 → 必须写 ADR（背景 / 选项 / 成本 / 不可逆点 / 回滚），并在 PR 中链接。
- ADR 至少保留 30 天再评估是否升级为正式决策。
